### Agent-mode / embedded-agent tools (these matter)

Three distinct mechanisms:

1. **`search_events` and `search_issues` take natural language and translate it to Sentry query syntax using an embedded LLM.** `search_issues` calls `hasAgentProvider()` and, when true, runs `searchIssuesAgent` with a repair prompt (`packages/mcp-core/src/tools/catalog/search-issues.ts:151`–`packages/mcp-core/src/tools/catalog/search-issues.ts:179`); the repair prompt literal is at `packages/mcp-core/src/tools/catalog/search-issues.ts:19`. `search_events` does the same for dataset + query + fields + sort (`packages/mcp-core/src/tools/catalog/search-events.ts:522`), with a second "validation repair" agent span named `search_events.validation_repair` at `packages/mcp-core/src/tools/catalog/search-events.ts:735`. Both degrade gracefully: `withProviderFallback` supplies a fallback that keeps the user's original query when the provider is down (`packages/mcp-core/src/tools/catalog/search-issues.ts:158`, `packages/mcp-core/src/tools/catalog/search-events.ts:526`). Agent sources live in `packages/mcp-core/src/tools/support/search-events/agent.ts`, `packages/mcp-core/src/tools/support/search-issues/agent.ts`, `packages/mcp-core/src/tools/support/search-issue-events/`. README calls this out at `README.md:36`.
2. **`analyze_issue_with_seer`** hands the issue to Sentry's server-side Seer autofix agent, polls state, and streams back root cause + code fixes (`packages/mcp-core/src/tools/catalog/analyze-issue-with-seer.ts:120`–`packages/mcp-core/src/tools/catalog/analyze-issue-with-seer.ts:170`). It requires **no Sentry API scopes** — authorization is purely by the `seer` skill (`packages/mcp-core/src/tools/catalog/analyze-issue-with-seer.ts:35`).
3. **`search_sentry_tools` + `execute_sentry_tool`** are a tool-catalog indirection layer (dynamic tool discovery), not LLM agents. `search_sentry_tools` returns structured JSON with per-tool JSON Schemas (`packages/mcp-core/src/tools/special/search-tools.ts:20`); `execute_sentry_tool` validates arguments against the target schema and dispatches inside its own `mcp.execute_tool` span (`packages/mcp-core/src/tools/special/execute-tool.ts:40`).

## Auth model

**Three auth paths.**

1. **stdio, user auth token.** `--access-token=<token>` or `SENTRY_ACCESS_TOKEN` (`packages/mcp-server/src/cli/usage.ts:16`, `:45`). README lists the required Sentry User Auth Token scopes verbatim at `README.md:38`–`:47`: `org:read`, `project:read`, `project:write`, `team:read`, `team:write`, `event:write`. The canonical scopes constant is `packages/mcp-core/src/scopes.ts:2`:
   ```ts
   // https://docs.sentry.io/api/permissions/
   export const SCOPES = {
     "org:read": "Read organization data",
     "project:write": "Write project data",
     "team:write": "Write team data",
     "event:write": "Write event data",
   };
   ```
   (write scopes imply read via the hierarchy in `packages/mcp-core/src/permissions.ts:33`.)
2. **stdio, OAuth device code flow (sentry.io only).** `sentry-mcp auth login|logout|status` (`packages/mcp-server/src/cli/usage.ts:10`–`:12`). Public OAuth client, no secret: `DEFAULT_SENTRY_CLIENT_ID = "0acbeba7d07d58076dd7dbde8cea2fed8ab525ce3713bda604988009ab35d765"` (`packages/mcp-server/src/auth/constants.ts:11`), endpoints `/oauth/device/code/` and `/oauth/token/` (`:14`, `:15`), always against `OAUTH_HOST = "sentry.io"` regardless of region (`:31`). Requested scopes = `Object.keys(SCOPES).join(" ")` (`:16`). Device flow is skipped for non-sentry.io hosts (`packages/mcp-server/src/auth/resolve-token.ts:29`); tokens are cached (`packages/mcp-server/src/auth/token-cache.ts`).
3. **Remote (Cloudflare worker).** Full OAuth: authorize route requests `scope: Object.keys(SCOPES).join(" ")` (`packages/mcp-cloudflare/src/server/oauth/routes/authorize.ts:51`); advertised as `scopes_supported` in AS metadata (`packages/mcp-cloudflare/src/server/authorization-server-metadata.ts:59`) and PRM (`packages/mcp-cloudflare/src/server/protected-resource-metadata.ts:18`). **Alternative:** a raw upstream Sentry token via the `Sentry-Bearer` HTTP auth scheme — deliberately distinct from `Bearer` (reserved for MCP OAuth access tokens); the worker does not store, validate, exchange, or refresh it (`README.md:84`–`:95`).

**Per-tool scopes.** Every tool declares `requiredScopes: Scope[]`, but the field is annotated `LEGACY … (deprecated, for backward compatibility)` at `packages/mcp-core/src/tools/types.ts:88`. The **live** authorization gate is `skills` — `isAllowedBySkills` in `packages/mcp-core/src/tools/catalog-runtime/availability.ts:86`, which returns `false` outright when no skills are granted (`:98`). `analyze_issue_with_seer` has `requiredScopes: []` and relies solely on the `seer` skill (`packages/mcp-core/src/tools/catalog/analyze-issue-with-seer.ts:35`). Skill selection: `--skills`, `--all-skills`, `--disable-skills`, `MCP_DISABLE_SKILLS` (`packages/mcp-server/src/cli/usage.ts:36`–`:39`, `:54`), or query params `?skills=` / `?disable-skills=` on the remote endpoint (`README.md:97`–`:98`).

**Org/project slug handling.** Session "constraints" (`organizationSlug`, `projectSlug`, `regionUrl`) are **stripped from the advertised input schema and re-injected server-side**, so a client cannot override them: `getFilteredInputSchema` (`packages/mcp-core/src/tools/catalog-runtime/availability.ts:121`) + `injectConstraintParams` (`:136`), backed by `packages/mcp-core/src/internal/constraint-helpers.ts:35` and `:66`. `projectSlug` aliases onto a tool's `projectSlugOrId` param (`constraint-helpers.ts:52`–`:59`). Constrained sessions also hide tools that would be meaningless: `find_organizations` when an org is pinned, `find_projects` and `create_project` when a project is pinned (`availability.ts:114`–`:118`). Remote deployments derive constraints from RFC 8707 `resource` URLs of the form `https://host/mcp/<org>/<project>` (`packages/mcp-cloudflare/src/server/oauth/resource-scope.ts:5`–`:32`), and OAuth token org/project constraints are re-checked per request (`packages/mcp-cloudflare/src/server/lib/mcp-handler.ts:386`, field declared at `:61`). CLI equivalents: `--organization-slug` / `--project-slug` (`packages/mcp-server/src/cli/usage.ts:33`–`:34`).

**`SENTRY_HOST` / self-hosted.** Supported. `SENTRY_HOST` env (`packages/mcp-server/src/cli/parse.ts:83`, `README.md:114`) or `--host` / `SENTRY_URL` (`packages/mcp-server/src/cli/resolve.ts:47`); unset defaults to Sentry SaaS (`README.md:138`–`:139`). Plain-HTTP self-hosted needs `--insecure-http`, which is rejected for real Sentry hosts (`packages/mcp-server/src/cli/resolve.ts:49`). `--access-token` is **required** for self-hosted since device code is sentry.io-only (`packages/mcp-server/src/cli/usage.ts:16`–`:18`). Seer and other SaaS-only features are disabled via `--disable-skills=seer` / `MCP_DISABLE_SKILLS=seer` (`README.md:60`–`:65`, `:141`–`:157`).

## Pagination

Three different strategies coexist — there is no single scheme.

1. **Hard cap + `hasMore`, no cursor.** `const RESULT_LIMIT = 25` in `find_projects` (`packages/mcp-core/src/tools/catalog/find-projects.ts:15`), `find_organizations` (`find-organizations.ts:9`), `find_teams` (`find-teams.ts:14`), `find_releases` (`find-releases.ts:13`). The handler requests `RESULT_LIMIT + 1` from the API, slices to `RESULT_LIMIT`, and reports `hasMore: results.length > RESULT_LIMIT` (`find-projects.ts:67`, `:72`, `:74`). The tool description tells the model to narrow instead of paging: `` `Returns up to ${RESULT_LIMIT} results. When hasMore is true, use the query parameter to narrow down results.` `` (`find-projects.ts:38`; `find-releases.ts:58`). `find_monitors` and `find_uptime_monitors` use the same `limit + 1` / `hasMore` trick with a caller-supplied `limit` (`find-monitors.ts:222`, `:255`; `find-uptime-monitors.ts:111`, `:123`).
2. **Real opaque cursors** (only 3 tools): `find_alert_rules` (`cursor`: string \| null, `limit`: int ≤100 default 10 — `packages/mcp-core/src/tools/catalog/find-alert-rules.ts:124`, `:132`), `find_dashboards` (`cursor` + `limit` ≤100 default 10 — `find-dashboards.ts:259`, `:267`; it wraps a custom base64 cursor `{v, apiCursor, offset, pageLimit}` validated at `:52`–`:62` and rejects foreign cursors with `"Invalid dashboard cursor. Pass the cursor exactly as returned by find_dashboards."` at `:105`), and `get_issue_user_reports` (`cursor` + `limit` ≤100 default 25 — `get-issue-user-reports.ts:70`, `:76`), which appends `` `- More user reports are available. Pass \`cursor: "${nextCursor}"\` with the same issue scope to fetch the next page.` `` (`:130`).
3. **Plain `limit` only.** `search_events` `limit` 1–100 default 10 (`search-events.ts:444`), `search_issues` `limit` 1–100 default 10 (`search-issues.ts:93`), `search_ai_conversations` 1–100 default 10 (`search-ai-conversations.ts:237`), `get_issue_activity` ≤100 default 25 (`get-issue-activity.ts:79`), `search_docs` `maxResults` 1–10 default 3 (`search-docs.ts:60`), `search_sentry_tools` `limit` ≤`MAX_LIMIT = 20`, default `DEFAULT_LIMIT = 8` (`search-tools.ts:10`, `:11`, `:90`).

Underneath, the API client translates all of this to Sentry's `per_page` + `Link`-header cursor (`packages/mcp-core/src/api-client/client.ts:1558`, `:1643`, `:1739`) and has an auto-paginating loop pinned at `per_page=100` that follows `getNextCursor(response.headers.get("link"))` until exhausted (`packages/mcp-core/src/api-client/client.ts:1904`–`:1926`, cursor parse at `:225`). `get_issue_details` issues one internal call with `limit: 10000` (`get-issue-details.ts:383`).

## Rate limits

**Server-side rate limiting exists only on the Cloudflare remote transport; none in `mcp-core` or the stdio server.** Cloudflare `unsafe.bindings` in `packages/mcp-cloudflare/wrangler.jsonc:28`–`:66` define four `ratelimit` namespaces (all `period: 60` seconds): `CHAT_RATE_LIMITER` limit 10 (`:31`–`:37`), `SEARCH_RATE_LIMITER` limit 20 (`:40`–`:46`), `MCP_IP_RATE_LIMITER` limit 300 (`:49`–`:55`), `MCP_USER_RATE_LIMITER` limit 60 (`:58`–`:64`). Enforcement: per-IP at `packages/mcp-cloudflare/src/server/index.ts:228`–`:246` and per-user/token at `packages/mcp-cloudflare/src/server/lib/mcp-handler.ts:365`–`:384`, both returning HTTP 429 with `MCP_RATE_LIMIT_EXCEEDED_MESSAGE = "Rate limit exceeded. Please wait before trying again."` (`packages/mcp-cloudflare/src/server/utils/rate-limiter.ts:4`). Identifiers are SHA-256 hashed to 16 hex chars before being used as keys (`rate-limiter.ts:26`–`:36`). When the binding is absent (e.g. local dev) requests pass through unlimited (`rate-limiter.ts:78`–`:80`).

**Client-side (upstream Sentry 429):** no retry/backoff on 429 — the client only classifies it. `ApiRateLimitError extends ApiClientError` with an optional `retryAfter` (`packages/mcp-core/src/api-client/errors.ts:200`–`:211`), constructed from the response at `:302`–`:303`; `isRateLimitError()` at `:117`. Because it is an `ApiClientError`, a 429 is rendered to the model as an `**Input Error**` and **not** logged to Sentry (`packages/mcp-core/src/internal/error-handling.ts:253`).

## Error shapes

**Errors are never thrown across the MCP boundary.** The handler wrapper catches everything and returns `{ content: [{ type: "text", text: <formatted markdown> }], isError: true }` — with an explicit source comment: `"CRITICAL: Tool errors MUST be returned as formatted text responses, NOT thrown as exceptions… DO NOT change this to throw error - it breaks error handling!"` (`packages/mcp-core/src/server.ts:403`–`:426`).

Custom error classes: `UserInputError`, `ConfigurationError`, `LLMProviderError` in `packages/mcp-core/src/errors.ts:5`, `:17`, `:31`; API hierarchy `ApiError` → `ApiClientError` (4xx) / `ApiServerError` (5xx), with `ApiPermissionError` (403), `ApiNotFoundError` (404), `ApiValidationError` (400/422), `ApiAuthenticationError` (401), `ApiRateLimitError` (429) in `packages/mcp-core/src/api-client/errors.ts:19`, `:38`, `:126`, `:152`, `:170`, `:188`, `:200`, `:217`.

Literal rendering, all from `formatErrorForUser` (`packages/mcp-core/src/internal/error-handling.ts:169`), joined with `"\n\n"`:

- `UserInputError` (`:173`–`:179`):
  ```
  **Input Error**

  It looks like there was a problem with the input you provided.

  <error.message>

  You may be able to resolve the issue by addressing the concern and trying again.
  ```
- `ConfigurationError` (`:182`–`:192`): `**Configuration Error**` / `There appears to be a configuration issue with your setup.` / message / `Please check your environment configuration and try again.` — **but on `transport === "http"` the detail is suppressed**, logged to Sentry, and replaced by `**Feature Unavailable**` / `This feature is temporarily unavailable due to a server configuration issue.` / `The service operator has been notified. Please try again later.` (`:67`–`:71`, `:115`–`:125`).
- `LLMProviderError` / AI SDK `APICallError` / `RetryError` (`:195`–`:231`): `**AI Provider Error**` / one of `The AI provider is currently unavailable.` (5xx) \| `The AI provider rejected this request.` (4xx) \| `The AI provider could not complete this request.` / message / `This is a service availability issue. Other non-AI tools should still work.` — on HTTP transport replaced by `**Feature Unavailable**` / `AI-powered features are temporarily unavailable because the upstream AI provider rejected or could not complete this request.` / `Other Sentry MCP tools that do not require AI should still work. Please try again later.` (`:73`–`:77`).
- `NoObjectGeneratedError` (`:235`–`:239`): `**AI Processing Error**` / `The AI was unable to process your query. Please try rephrasing your request.`
- Upstream 401, deep-checked through `{ cause }` chains (`:245`–`:249`): `**Authorization Expired**` / `Sentry rejected the stored access token for this session. Please re-authorize to continue.` It additionally invokes `context.onUpstreamUnauthorized()` so the transport can revoke the MCP grant (`packages/mcp-core/src/server.ts:394`–`:401`).
- `ApiClientError` 4xx (`:253`–`:263`): `**Input Error**` / `` `There was an HTTP ${status} error with your request to the Sentry API.` `` / `error.toUserMessage()` / `You may be able to resolve the issue by addressing the concern and trying again.` `toUserMessage()` yields `` `API error (${status}): ${message}` `` and for generic 404s appends `. Please verify that the organization, project, or resource ID is correct and that you have access to it.` (`packages/mcp-core/src/api-client/errors.ts:55`–`:83`).
- `ApiServerError` 5xx (`:267`–`:278`): logged to Sentry, then `**Error**` / `` `There was an HTTP ${status} server error with the Sentry API.` `` / message / `` `**Event ID**: ${eventId}` `` / `Please contact support if the problem persists.`
- Unknown (`:295`–`:311`): `**Error**` / `It looks like there was a problem communicating with the Sentry API.` / `Please report the following to the user for the Sentry team:` / `` `**Event ID**: ${eventId}` `` (raw message appended only when `NODE_ENV !== "production"`).

Security note in the same file (`:166`–`:167`): *"SECURITY: Only return trusted error messages to prevent prompt injection vulnerabilities."*

**Schema-validation errors** are converted to `UserInputError` before dispatch: `` `Invalid arguments for ${tool.name}: ${formatZodIssues(error)}` `` where each issue renders as `` `${path.join(".")}: ${message}` `` joined by `"; "` (`packages/mcp-core/src/tools/catalog-runtime/availability.ts:228`–`:235`, `:264`–`:268`).

**"Too many results" is not an error — it is degraded output.** The server has no result-count failure mode. Instead: (a) `hasMore: true` in structuredContent plus a description telling the model to narrow the `query` (`packages/mcp-core/src/tools/catalog/find-projects.ts:38`, `find-monitors.ts:149`, `find-uptime-monitors.ts:34`); (b) markdown `Found **N** issue(s)` headers (`packages/mcp-core/src/tools/support/search-issues/formatters.ts:101`); (c) per-field truncation for AI conversations — values are cut at `MAX_RAW_GEN_AI_ATTRIBUTE_LENGTH` and suffixed `"... [truncated]"`, with the affected keys listed in a `truncatedFields: string[]` output field (`packages/mcp-core/src/tools/catalog/get-ai-conversation-details.ts:244`–`:254`, `:114`); (d) `get_snapshot_image` warns in-description that `imageResolution="full"` "can substantially increase response size and token usage" (`get-snapshot-image.ts:20`, `:60`). Docs policy on the "more results" phrasing: `docs/contributing/tool-responses.md:200` — *"Good: `More results are available. Pass cursor: "..." with the same scope.`"*.

**Expected-vs-unexpected classification** decides Sentry issue creation: `isExpectedToolError` (`packages/mcp-core/src/internal/error-handling.ts:86`) treats `UserInputError`, `ConfigurationError`, `LLMProviderError`, `ApiClientError` (all 4xx incl. 429), deep-401, AI-SDK `APICallError`/`RetryError`/`NoObjectGeneratedError` as expected — span marked failed, no exception recorded (`packages/mcp-core/src/server.ts:386`–`:388`).
