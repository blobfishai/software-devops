## Auth model
- **Env var: `PAGERDUTY_USER_API_KEY`** — read at client construction: `api_key = os.getenv("PAGERDUTY_USER_API_KEY")` (`pagerduty_mcp/context/application_context_strategy.py:20`). Missing ⇒ `RuntimeError("An API key is required to call the PagerDuty API.")` (`pagerduty_mcp/context/application_context_strategy.py:23-24`). Declared required in `server.json` (`server.json:27-30`) and README config table (README.md:370).
- **Env var: `PAGERDUTY_API_HOST`**, default `"https://api.pagerduty.com"` (`pagerduty_mcp/context/application_context_strategy.py:21`), applied as `pd_client.url = api_host` (`pagerduty_mcp/context/application_context_strategy.py:27-28`). EU accounts use `https://api.eu.pagerduty.com` (README.md:371). `.env` is loaded via `load_dotenv()` (`pagerduty_mcp/context/context_resolver.py:11`).
- **REST API v2 key, not OAuth.** The client subclasses `pagerduty.rest_api_v2_client.RestApiV2Client` and is constructed with the raw key: `PagerdutyMCPClient(api_key)` (`pagerduty_mcp/context/application_context_strategy.py:5,12-15,26`). There is no OAuth code path, no token refresh, no `Authorization: Bearer` construction anywhere in `pagerduty_mcp/`. A custom `user_agent` prefixes `pagerduty-mcp/<version>` (`pagerduty_mcp/context/application_context_strategy.py:13-15`, `pagerduty_mcp/__init__.py:1`).
- **`From` header — confirmed in source, and set automatically.** On context construction the server calls `GET /users/me` and, on success, sets `self.client.headers["From"] = user.email` (`pagerduty_mcp/context/mcp_context.py:21-27`). If that call fails (e.g. an account-level/global REST key, which has no `/users/me`), the exception is swallowed with a warning and `user` stays `None` (`pagerduty_mcp/context/mcp_context.py:31-34`) — so no `From` header is sent. Consequences visible in source:
  - `add_responders` returns the literal string `"Cannot add responders with account level auth. Please provide a user token."` instead of calling the API (`pagerduty_mcp/tools/incidents.py:213-215`); it also injects `payload["requester_id"] = user.id` (`pagerduty_mcp/tools/incidents.py:217-218`).
  - `list_incidents(request_scope='assigned'|'teams')` raises `ValueError("Cannot filter incidents by \"{request_scope}\" with account-level auth. Please provide a user token, or scope the request differently.")` (`pagerduty_mcp/tools/incidents.py:64-67`).
  - `list_teams(scope='my')` raises `ValueError("Cannot fetch 'my' teams with account-level auth. Please provide a user token, or scope the request differently.")` (`pagerduty_mcp/tools/teams.py:30-37`).
- **Multi-tenant / per-request auth** is supported architecturally: `ContextResolver.set_strategy(...)` with `RequestContextStrategy` + `ContextResolver.use_context(MCPContext(client=...))` (`pagerduty_mcp/context/context_resolver.py:39-51`, `pagerduty_mcp/context/request_context_strategy.py:8-26`). The shipped server hardcodes the single-tenant `ApplicationContextStrategy()` (`pagerduty_mcp/server.py:94`).
- **Required scopes: NOT DETERMINED FROM SOURCE.** No scope strings or scope checks appear anywhere in the repo; README only instructs creating a User API Token from *User Settings → API Access* and notes Freemium role limits (README.md:68-77).

## Pagination
- **Central helper:** `paginate(*, client, entity, params, maximum_records: int = MAX_RESULTS)` (`pagerduty_mcp/utils.py:5`). It iterates `client.iter_all(entity, params=params)` and **breaks once `count >= maximum_records`** (`pagerduty_mcp/utils.py:21-25`) — i.e. cursor/offset paging is delegated to the `pagerduty` SDK's `iter_all`, and the MCP layer only imposes a hard record cap.
- **Constants:** `DEFAULT_PAGINATION_LIMIT = 20`, `MAXIMUM_PAGINATION_LIMIT = 100`, `MAX_RESULTS = 1000` (`pagerduty_mcp/models/base.py:7-9`). Query models bound `limit` with `ge=1, le=MAXIMUM_PAGINATION_LIMIT` (100) — e.g. `ScheduleQuery` (`pagerduty_mcp/models/schedules.py:105-110`), `ServiceQuery` (`pagerduty_mcp/models/services.py:29-34`), `UserQuery` (`pagerduty_mcp/models/users.py:55-60`), `OncallQuery` (`pagerduty_mcp/models/oncalls.py:43-48`), `TeamQuery` (`pagerduty_mcp/models/teams.py:38-43`), `EscalationPolicyQuery` (`pagerduty_mcp/models/escalation_policies.py:128-133`); `LogEntryQuery.limit` and `AlertQuery.limit` instead use `le=MAX_RESULTS` (1000) with default 100 (`pagerduty_mcp/models/log_entries.py:77-82`, `pagerduty_mcp/models/alerts.py:70-75`).
- **Hard caps, per tool (exact numbers):**
  - `list_incidents`: `maximum_records=limit or MAX_RESULTS` ⇒ **1000** (`pagerduty_mcp/tools/incidents.py:75-77`).
  - `list_services`, `list_escalation_policies`, `list_schedules` (v2 half): `paginate(...)` called **without** `maximum_records`, so the default **1000** applies; the tool's `limit` is only forwarded as an API page-size param (`pagerduty_mcp/tools/services.py:29-31`, `pagerduty_mcp/tools/escalation_policies.py:36-38`, `pagerduty_mcp/tools/schedules.py:120`).
  - `list_oncalls`: `maximum_records=limit or 1000` (`pagerduty_mcp/tools/oncalls.py:68-70`); also sets `params["limit"]` and `params["earliest"]` (`pagerduty_mcp/tools/oncalls.py:54-57`).
  - `list_teams`: `maximum_records=limit or 1000`; the `scope='my'` branch always uses **1000** and filters client-side (`pagerduty_mcp/tools/teams.py:43,51`). `list_team_members`: **1000** (`pagerduty_mcp/tools/teams.py:121`).
  - `list_log_entries`: `maximum_records=query_model.limit or 100` (`pagerduty_mcp/tools/log_entries.py:46-51`); defaults `since`/`until` to the **last 7 days** when unset (`pagerduty_mcp/tools/log_entries.py:39-42`).
  - `list_alerts_from_incident`: `limit`/`offset` sent as params, `maximum_records=limit or 100` (`pagerduty_mcp/tools/alerts.py:66-77`).
  - `list_change_events` / `list_service_change_events`: `limit`(default 100)/`offset`/`total` params, `maximum_records=limit or 100` (`pagerduty_mcp/tools/change_events.py:35-56`).
  - `list_alert_grouping_settings`: **cursor-based** — `after` / `before` cursor params plus `limit` default **1000**, `maximum_records=limit or 1000` (`pagerduty_mcp/tools/alert_grouping_settings.py:15-51`).
  - `list_priorities`: `maximum_records=100` (`pagerduty_mcp/tools/priorities.py:13-18`).
  - `list_users`: **no pagination at all** — a single `client.rget("/users", params=params)` with `limit` default 100 (`pagerduty_mcp/tools/users.py:41`).
- **`more` flag handling:** only the v3 schedules path reads it. `_get_v3_schedules_page` returns `(data["schedules"], bool(data.get("more")))` (`pagerduty_mcp/tools/schedules_v3.py:108-109`), which surfaces as `SourceStatus.more` (`pagerduty_mcp/tools/schedules.py:132`; field at `pagerduty_mcp/models/schedules.py:224`) and produces the summary line `"- Note: more {label} schedules exist beyond the returned page."` (`pagerduty_mcp/models/schedules.py:260-261`). Elsewhere the `more`/`offset` bookkeeping is inside the SDK's `iter_all` and is not inspected by this repo.
- **v3 endpoints bypass the SDK path allowlist**: `client.get/post/put/delete` with a manually built URL, because `rget` et al. validate against a hardcoded `CANONICAL_PATHS` list that lacks `/v3/schedules` (`pagerduty_mcp/tools/schedules_v3.py:25-33`).

## Rate limits
- **No 429 handling, retry, or backoff exists in this repository.** Grepping `429|retry|backoff|max_http_attempts|sleep_timer` across `pagerduty_mcp/` returns zero matches (only eval-harness LLM retries under `tests/evals/`, e.g. `tests/evals/llm_clients/bedrock_client.py:23-43`, which throttle Bedrock, not PagerDuty).
- Whatever retry/backoff exists comes from the third-party SDK's `RestApiV2Client` (`pagerduty~=5.3`, `pyproject.toml:10`; instantiated at `pagerduty_mcp/context/application_context_strategy.py:26`). The SDK is not vendored in this repo, so its exact 429 policy is **NOT DETERMINED FROM SOURCE**.
- One indirect amplification risk worth noting for mocks: `list_oncalls` issues one extra `GET /services/{id}` per entry in `service_ids` before the main query (`pagerduty_mcp/tools/oncalls.py:60-66`), and `list_schedules` issues up to **50** extra per-ID v3 GETs to enrich names (`_V3_ENRICH_CAP = 50`, `pagerduty_mcp/tools/schedules.py:32`, used at `pagerduty_mcp/tools/schedules.py:69`).

## Error shapes
- **`ValueError`** (raised, propagates to the MCP layer):
  - `"incident_id must be a non-empty string"` (`pagerduty_mcp/tools/alerts.py:41`).
  - `"alert_id must be a non-empty string. To list all alerts for an incident, use list_alerts_from_incident instead."` (`pagerduty_mcp/tools/alerts.py:43-46`) — guarded by `_is_blank_id`, which strips quote/backtick/zero-width artifacts and rejects the literals `{"null", "none", "undefined", "nil"}` (`pagerduty_mcp/tools/alerts.py:10-22`).
  - `f"Cannot filter incidents by \"{request_scope}\" with account-level auth. Please provide a user token, or scope the request differently."` (`pagerduty_mcp/tools/incidents.py:67`).
  - `"Cannot fetch 'my' teams with account-level auth. Please provide a user token, or scope the request differently."` (`pagerduty_mcp/tools/teams.py:34-37`).
  - `f"Event orchestration {orchestration_id} has no valid router configuration"` (`pagerduty_mcp/tools/event_orchestrations.py:121`).
  - Pydantic validator: `'The correct parameter to filter by multiple Incidents statuses is "status", not "statuses", please correct your input and try again'` (`pagerduty_mcp/models/incidents.py:78-81`) — note this lives on `IncidentQuery`, which the registered `list_incidents` tool does **not** use (it takes flat args, `pagerduty_mcp/tools/incidents.py:27-35`).
  - Response-shape guards: `"Empty response from outlier incident endpoint"` and `f"Unexpected response format: {type(response_data)}"` (`pagerduty_mcp/models/incidents.py:376,386,440,484`).
- **`RuntimeError`**:
  - v3 schedules: `f"PagerDuty v3 Schedules API error (HTTP {status}): {_extract_api_message(resp)}"` (`pagerduty_mcp/tools/schedules_v3.py:89`), where the message is unwrapped from `body["error"]["message"]` joined with `body["error"]["errors"]` (`pagerduty_mcp/tools/schedules_v3.py:59-77`). The docstring calls out surfacing the API's own text, e.g. `"This is a layer-based schedule. Use the v2 Schedules API to access it."` (`pagerduty_mcp/tools/schedules_v3.py:83-84`).
  - `"An API key is required to call the PagerDuty API."` (`pagerduty_mcp/context/application_context_strategy.py:24`).
  - `"No context strategy is available"` (`pagerduty_mcp/context/context_resolver.py:63`).
- **`pagerduty.errors.HttpError`** from the SDK is the only third-party exception explicitly caught, and only for the v2→v3 schedule redirect: a 400 whose message contains any of `("shift-based", "v3 schedules api", "/v3/schedules")` triggers a v3 retry; anything else re-raises (`pagerduty_mcp/tools/schedules.py:4,145-156,178-183`).
- **Errors returned as plain strings instead of raising** (silent-success hazard for mocks): `"Cannot add responders with account level auth. Please provide a user token."` and `"Unexpected response format: " + str(response)` (`pagerduty_mcp/tools/incidents.py:215,224`); `"Successfully added user to team"` / `f"Failed to add user to team: {response.reason}"` (`pagerduty_mcp/tools/teams.py:139-140`); `f"Successfully deleted team {team_id}"` (`pagerduty_mcp/tools/teams.py:109`); `f"Successfully removed user {user_id} from team {team_id}"` (`pagerduty_mcp/tools/teams.py:154`).
- **Degrade-don't-fail:** `list_schedules` catches `Exception` per source and records `SourceStatus(api=..., status="error", message=str(exc))` rather than raising (`pagerduty_mcp/tools/schedules.py:119-136`); per-item v3 name enrichment failures are logged and counted, never fatal (`pagerduty_mcp/tools/schedules.py:76-78`).
- **Truncation / "too many results" guard:** `ListResponseModel.response_summary` always emits `"ListResponseModel<{entity_type}>:"` + `"- Returned {count} record(s) of type '{entity_type}'."`, and when `count == MAX_RESULTS` (1000) appends `"- WARNING: The number of records equals the response limit. There may be more records not included in this response."` (`pagerduty_mcp/models/base.py:24-46`, threshold at `pagerduty_mcp/models/base.py:41`). `SchedulesListResponse` overrides it with per-source counts, a hard `"- WARNING: the {label} source FAILED — this list is INCOMPLETE. Do not tell the user these schedules do not exist. ({source.message})"`, and `"- WARNING: the number of records equals the response limit; there may be more not included."` at `count >= MAX_RESULTS` (`pagerduty_mcp/models/schedules.py:241-264`). There is **no** byte-size/token truncation of large incident payloads anywhere — only the 1000-record cap in `paginate` (`pagerduty_mcp/utils.py:24-25`).
- How a raised exception is rendered to the model is the FastMCP layer's job (`mcp[cli]~=1.8`, `pyproject.toml:9`) and is **NOT DETERMINED FROM SOURCE** in this repo.

## Notes for mocking
- **Incident status lifecycle:** the readable set is `Literal["triggered", "acknowledged", "resolved"]` (`pagerduty_mcp/models/incidents.py:9`), but the *writable* set via `manage_incidents` is only `Literal["acknowledged", "resolved"]` (`pagerduty_mcp/models/incidents.py:11`) — a mock must reject/never expect a transition back to `triggered`. Status changes are `PUT /incidents` with a bulk body `{"incidents": [{"type": "incident_reference", "id": ..., "status": ...}]}` (`pagerduty_mcp/tools/incidents.py:108-147`).
- **Urgency** is always `Literal["high", "low"]` on read, create, and manage (`pagerduty_mcp/models/incidents.py:13-19,239,272`); `IncidentCreate.urgency` defaults to `"high"` (`pagerduty_mcp/models/incidents.py:239`).
- **Priority is a reference, not a string.** `Incident.priority: PriorityReference` (`id`, `summary`, computed `type="priority_reference"`) — `pagerduty_mcp/models/incidents.py:216-219`, `pagerduty_mcp/models/references.py:46-47`. `list_incidents(priorities=[...])` expects priority **IDs** and maps them to `priority_ids[]`; passing names silently no-ops (`pagerduty_mcp/tools/incidents.py:59-62`). Mocks should back `list_priorities` (returns a JSON **string**, `pagerduty_mcp/tools/priorities.py:7,21`) so the ID lookup works.
- **Service → escalation policy is mandatory:** `Service.escalation_policy: EscalationPolicyReference` has no default (`pagerduty_mcp/models/services.py:14`). `list_oncalls(service_ids=[...])` relies on this: it GETs each service and substitutes `service.escalation_policy.id` into `escalation_policy_ids[]` (`pagerduty_mcp/tools/oncalls.py:60-66`).
- **Escalation policy → targets:** each `EscalationRule` needs `escalation_delay_in_minutes` and ≥1 target of type `user_reference`, `schedule_reference`, or `schedule_v3_reference` (`pagerduty_mcp/models/escalation_policies.py:13-31`, tool docstring `pagerduty_mcp/tools/escalation_policies.py:60-62`). `num_loops` defaults to 0 and `on_call_handoff_notifications` to `"if_has_services"` (`pagerduty_mcp/models/escalation_policies.py:63-70`).
- **Two schedule systems coexist.** `kind` discriminates: `"layer_based"` (v2, `GET /schedules/{id}`, has `schedule_layers`) vs `"shift_based"` (v3, `GET /v3/schedules/{id}`, has rotations/custom shifts/overrides) — `pagerduty_mcp/models/schedules.py:46-49,193,208-210`. A mock v2 GET on a v3 schedule should return **HTTP 400** whose `error.message` contains one of `"shift-based" / "v3 schedules api" / "/v3/schedules"`, which is exactly what triggers the automatic v3 fallback (`pagerduty_mcp/tools/schedules.py:36,145-156,178-183`). `create_schedule`/`update_schedule` always target v3 (`pagerduty_mcp/tools/schedules.py:186-211`), while `create_schedule_override` is v2 (`POST /schedules/{id}/overrides`, `pagerduty_mcp/tools/schedules.py:233`).
- **v3 list responses need a `more` boolean and a `schedules` key**: `{"schedules": [...], "more": bool}` (`pagerduty_mcp/tools/schedules_v3.py:108-109`); v3 items may omit `name`, which triggers up to 50 per-ID enrichment GETs (`pagerduty_mcp/tools/schedules.py:32,66-78`).
- **`GET /users/me` is called once at startup** and its `email` becomes the `From` header for all subsequent writes (`pagerduty_mcp/context/mcp_context.py:21-27`). A mock that 404s/403s this endpoint puts the server in "account-level auth" mode and changes the behavior of `add_responders`, `list_incidents(request_scope=...)`, and `list_teams(scope='my')` (see **Auth model**).
- **Wrapped vs unwrapped responses:** many tools accept both `{"service": {...}}` and a bare `{...}` (`pagerduty_mcp/tools/services.py:67-70`, `pagerduty_mcp/tools/teams.py:76-79`, `pagerduty_mcp/tools/escalation_policies.py:69-72`, `pagerduty_mcp/tools/schedules_v3.py:36-56`), and past/related/outlier incident endpoints accept a wrapped dict, a bare dict, or a bare list (`pagerduty_mcp/models/incidents.py:356-386,408-440,458-484`). `list_incident_notes` expects a bare list and silently returns `[]` otherwise (`pagerduty_mcp/tools/incidents.py:240-245`).
- **Roles:** user roles are `admin | limited_user | observer | owner | read_only_user | restricted_access | read_only_limited_user | user` (`pagerduty_mcp/models/users.py:8-17`); team membership roles are `observer | responder | manager` with default `manager` (`pagerduty_mcp/models/teams.py:12`, `pagerduty_mcp/models/teams.py:72-77`), and `TeamCreate.default_role` is `manager | none` (`pagerduty_mcp/models/teams.py:11,60-63`).
- **Log entries are polymorphic and permissive:** `LogEntry` uses `extra="allow"` with `self` aliased to `self_`, and `incident` typed as a raw `dict` (`pagerduty_mcp/models/log_entries.py:42-61`). Same `extra="allow"` + `self` alias applies to `Alert` (`pagerduty_mcp/models/alerts.py:44-62`). Mock payloads can carry arbitrary extra fields without validation failure, but **must** include `id`, `self`, `created_at` (and for alerts `type`, `summary`, `html_url`, `status`, `alert_key`), which are non-optional.
