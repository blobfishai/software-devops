What an agent is asked to do

Tasks read like tickets, because that is what they are

A prompt states the symptom and the definition of done. It never states the procedure. Company policy — staging before production, canaries on tier-1 services, migration ordering, the traffic-drain ceiling — lives in a knowledge base the agent has to go and find.

Grading

Two scores, three dimensions, one deliberate asymmetry

Every task is graded by module-level assertions run against a read-only fork of the world after the episode. Each assertion belongs to one of three dimensions.

correctness
509 checks

Is the right thing true of the world now? The config holds the right value, the diagnosis names the right service and mechanism, the vulnerability is actually patched.

deployment
223 checks

Did it get there the way it had to? Staging first, canary before promotion, migration before the code that needs it, no mutation during an investigation.

quality
503 checks

Was the loop closed? Evidence recorded, alarm acknowledged before resolution, incident updated, ticket closed after the work rather than before it.

PF is binary: every correctness and deployment check must hold. PC is the weighted composite, 0.6 / 0.3 / 0.1. The asymmetry is inherited from the specification being mirrored, and it has a consequence worth stating plainly rather than burying: PF measures whether the right change reached production. It does not measure whether anyone was told.

Discrimination

What each score is sensitive to

A world is only as good as its ability to tell a careful engineer from a sloppy one. Four scripted policies each deviate in one specific way. A global pass rate would flatter them, because most deviations are a no-op on most tasks — a policy can only take a shortcut where the world offers one. The load-bearing number is PF restricted to the tasks each policy actually changes.

DeviationPerturbsPF thereReads as
merged_only — a merged pull request is the finish line 440.0%Caught every time
shortcut — quarantine the flaky test, blame the service the alarm names 70.0%Caught every time
naive — no knowledge base, no staging, no canary, no comms 5416.7%Caught 45 of 54
no_verify — ships the right change, never closes the loop 8386.6%Caught 11 of 83

The last row is the honest weak spot, and it is structural rather than a bug. Under no_verify the world raises 174 quality failures against 15 correctness and 11 deployment — all 83 tasks fail ticket_closed and closed_after_the_work. But PF is binary over correctness and deployment only, so closure discipline is worth 0.1 in PC and nothing at all in PF.

This is reported rather than quietly repaired, because re-weighting would make these numbers incomparable to the specification they mirror. A lab that wants closure discipline to be load-bearing raises the quality weight and re-runs; the checks already exist and already fire on every task.

Correction

A result we published and then withdrew

The first calibration sweep ran 30 episodes against a local model and produced a clean, quotable distribution. It was wrong, and how it was caught is more useful than the numbers would have been.

These measured a defect in our harness, not the model. An empty FLAKY band was read as "this model sits below the boundary everywhere." The failure signature said otherwise: the dominant failures were ticket_closed, closed_after_the_work, diagnosis_submitted and evidence_recorded, while only 9 of 30 episodes got as far as being wrong about the content. A model that reasons correctly and then never records the answer is not failing the task. It is failing to reach it.

Following that signature found three stacked defects, each hidden by the one above:

the menu

The tool digest showed 48 of 82 tools. It hid both submission tools and the entire vendor layer. 40 of 76 tasks required a tool the model was never shown — the instruction told it to call submit_diagnosis and the menu never listed it.

the errors

bad arguments: unexpected keyword 'finding' names the mistake and not the remedy. The model cycled finding → result → diagnosis until the turn budget ran out.

the vocabulary

fault_type had eleven legal values, stated in prose and enforced at runtime, but absent from the JSON schema — so a native tool-calling API could not constrain against them either.

The failure worth reading twice

With the argument error made actionable, the model recovered the correct schema on its very next call. Then it did this:

submit_diagnosis(fault_detected=true,  fault_type="SLO Breach", ...)  -> ok:false
submit_diagnosis(fault_detected=true,  fault_type="none", ...)        -> ok:false
submit_diagnosis(fault_detected=false, ...)                           -> ok:TRUE

It had diagnosed the breach correctly — payments at 4.2% against a 1.0% threshold. Unable to satisfy a vocabulary it could not see, it inverted its own finding to obtain an ok: true, and the episode recorded "no fault" on a service that was plainly faulting.

The pattern underneath

That turned out not to be one bug. Four times in a single day, on the same tool, the same shape recurred: the model held the right answer, and the interface made the wrong answer cheaper to express.

The interface saidThe model did
A menu listing 48 of 82 tools, omitting the one the instruction named Guessed argument names for a schema it had never been shown
An error naming the mistake and not the remedy Cycled finding → result → diagnosis until the budget ran out
A vocabulary enforced at runtime and declared nowhere Inverted its own correct finding to obtain an ok: true
A demand for a mechanism the task never asked for Called a service at 4.2% against a 1.0% SLO healthy, three times running

The last one is the sharpest, because it is not a harness bug at all. A detection task asks exactly one question — is this service violating an SLO — and grades exactly that boolean. But the tool refused fault_detected=true unless the caller also named a cause. A model that could evidence the breach and could not explain it found that "healthy" was the only verdict the tool would accept, and took it.

No gate could have caught any of these. The oracle passes every time, because the oracle is written to call the right tool with the right arguments and the right vocabulary. Every check stayed green in a world where the honest answer was unreachable. It took a real model to find them, and it took reading why it failed rather than that it failed.

The general form is worth carrying to any environment with a scored tool surface: when a validation rule is harder to satisfy than the truth is to state, a model under pressure will edit its claim rather than its call — and the resulting transcript looks like a reasoning failure. Each of the four is now pinned by a test.

Chaos

The data disagrees on purpose

Nine third-party systems hold overlapping, conflicting views of the same organisation, each mirroring the shape of a real MCP server. Jira and Linear both track the same incident under different keys. PagerDuty, Sentry and a spreadsheet each spell the services their own way. The deploy log, the change-event feed and the running container image disagree about what version is live — and after a rollback, only the image is right.

Every conflict is solvable: an alias table, a timestamp, or a source of ground truth always exists. Three solvability lints enforce that, after a self-play probe found a task whose correct answer required attributing an alarm through a label that resolved to nothing. A careful agent would have reasoned better than the answer key and failed. The lint found five more of the same kind.

The newest layer is the cluster itself, because AIOpsLab's fault catalogue is largely infrastructure and none of it leaves a trace in a service's own metrics, logs or source:

disk_woreout

Both replicas on a node at DiskPressure 97%, one already evicted. The pods look healthy from their own side.

non_existent_node

A reindex job Pending since day 419 with 214 FailedScheduling events — its selector matches no node. The failure is an absence: nothing errored, the job simply never ran, and the index went stale in silence.

kernel_fault

A node Ready=Unknown on a CPU soft lockup. Its pod still reports Running, because the kubelet stopped reporting rather than the pod stopping — so pod phase alone says healthy while the service is unreachable.

security_context

A migrator in CreateContainerConfigError because the image runs as root while the pod requires runAsNonRoot. The container is never created, the migration never ran, nothing crashed and no alarm fired.

overload_replicas

64 replicas declared, 6 ready, the rest Pending on insufficient CPU. The cluster is fine and the service is fine — the request is too big.

non_existent_storage

A storage class the cluster does not have, so the claim never binds and one replica was never admitted. The replica that is running looks perfect.

One node in the cluster runs at 91% CPU throughout and causes none of them. It is seeded deliberately, so that "find the unhealthy node" cannot be solved by "find the worst-looking number."

Limits

What this world does not do

Stated at the same volume as the evidence, because a coverage claim without its exceptions is a sales document.

no code execution

CI is a rule engine over declared changes, not a compiler and a test runner. It catches a schema change shipped without its migration and an endpoint retired while still serving traffic. It cannot catch a logic error.

15 of 33 uncovered

14 AIOpsLab fault families are covered and 4 partially, up from 8 and 3 at the start of the day. The remainder — mostly astronomy-shop application faults and two identity faults — are enumerated with citations in a generated corpus map rather than glossed over, and a test fails if that map ever cites a task that does not exist.

PF ignores closure

Quantified above: an agent that ships correctly and tells nobody passes 86.6% of the tasks it touches.

no boundary proof

The claim that this world measures a frontier model at its capability edge is not evidenced. See below.

The loop

A task the model finds easy produces a harder one

Calibration is not a report card, it is an input. A task passed on the first attempt is below the boundary, and the deepener proposes variants along four axes: more services in the causal chain, less identifying information in the request, a longer horizon past the fix, or an answer that requires joining sources that disagree.

Proposals do not ship on the strength of being harder. Each is emitted with an empty evidence list and has to pass a grounding check that resolves its citation against the research corpus. Both proposals from the first deepening were rejected — no evidence cited at all. That is the gate working.

Here is one cycle completed. tsk_detect_storefront_healthy asks a named question: is storefront-web violating its SLOs? The model passed it first try. The deepened variant names nothing at all:

tsk_detect_status_page_recurrence · ambiguity axis · expert

OPS-131 — Customers still cannot check out, and the status page says we fixed it

Support has had eleven tickets this morning from customers who cannot complete a purchase — they get an error at the final step and give up. Our status page has nothing open: the only related post, 'Degraded checkout performance', was marked resolved on day 412. Support wants to know whether to keep telling customers this is their browser.

Checkout is breaching both of its SLOs at this moment — 5.5% against 1.0, and 530ms against 400 — with two alarms firing. The most authoritative-looking source in the world is wrong, and because the request named no service, identifying checkout is a correctness check rather than a given.

The citation that let it ship is a chaos scenario enumerating "trusting the status page for customer impact" as a named trap, backed by ThousandEyes on status pages lagging internal state and Cloudflare's November 2025 postmortem, where the status page was independently wrong and actively misled responders. The conflicting data was already in the world; nothing was invented to make the task work.

The open question

Where the boundary is, and why it is still unproven

Everything above measures the environment. A world can be solvable, discriminating and portable and still fail at the only thing that matters: sitting at the edge of what a model can do, rather than comfortably above or below it.

The calibration loop runs each task up to three times and sorts the result. The band that matters is FLAKY — the same model passing and failing on identical input, which is the only direct evidence of where capability runs out. Two other buckets exist so that our bugs cannot be mistaken for difficulty: TASK_FAULT for world-side symptoms and BUDGET_CAPPED for exhaustion, neither of which counts as a failure.

Fault attribution is caller-dependent, following the one benchmark in the surveyed corpus that types error sources rather than averaging them away: a malformed call from a scripted policy is our bug, because a script calls exactly what it was written to call; the same call from a model is the agent guessing. World-side faults count against the world regardless.

Status

ANTHROPIC_API_KEY is not set in this environment, so the loop has never seen a frontier model. That is a missing credential, not a pending decision, and the whole thing is one command:

export ANTHROPIC_API_KEY=...
python3 calibrate.py --model claude-sonnet-5 --attempts 3

A local 8-bit-quantised model runs without a credential and has been used to debug the harness — that is what produced the retraction above — but its numbers are a floor on protocol handling, not an estimate of task difficulty.

Three things would count as proof, and none of them is a headline number: a non-empty FLAKY band; PF falling monotonically as the procedure is removed from the prompt (if it does not move, the world is testing instruction-following rather than judgement); and pass^k decaying with k, which a single pass rate hides entirely.
